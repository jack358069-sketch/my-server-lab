# 备份不是万能药：三份每日备份与一次真实的恢复演练

> 系列：个人服务器实验站复盘（二）
> 关键词：备份、恢复演练、1Panel、MariaDB、运维习惯

## 先算清楚：一旦丢数据，代价是什么

这台 2 核 2G 的 ECS 上跑着三样东西：静态站（含天气、状态数据）、LobeChat（`.env` 里有 API key 和访问密码）、Typecho 博客（内容全在 MariaDB 里）。

丢网站可以重传，丢 API key 要重新申请，**丢博客内容就是真的丢了**。所以备份优先级按这个顺序排：博客 > LobeChat > 静态站。

## 方案：三个时间点 + 保留 7 份

用 1Panel 的计划任务，每天晚上错开跑：

| 时间 | 对象 | 说明 |
|---|---|---|
| 03:00 | 网站 `47.115.150.227` | 页面、天气 JSON、状态数据 |
| 03:10 | LobeChat 应用目录 | 含 `.env` |
| 03:20 | Typecho + MariaDB | 数据库另行物理备份 |

保留 7 份，存 `/opt/1panel/backup`。错开十分钟是为了避免三个任务同时压缩，把 2 核机器顶满——小机器上，**备份本身也是一次负载事件**。

## 最容易忽略的一步：验证备份能不能解开

备份跑成功 ≠ 备份可用。做过一次恢复演练，步骤很朴素：

1. 取最新的站点包，解到临时目录，确认能解出页面、JSON、SVG 等文件；
2. 取最新的 MariaDB 包，确认是物理备份（两百多个文件），能正常解开；
3. 记下结论，清掉临时目录。

这一步花不到十分钟，但它回答了一个致命问题：**灾难发生那天，我手上的东西是不是坏的**。压缩包损坏、权限不对、备份时文件正在被写，都可能让备份"存在但没用"。

## 已知的边界：这份备份防不了什么

- **防不了磁盘损坏**。备份和源数据在同一块磁盘上，磁盘挂了两个一起没；
- **防不了误删面板**。1Panel 自身配置不在备份范围内，面板坏了要按文档重建；
- **不防勒索/误操作删除**。7 份滚动保留，如果连续 7 天没人发现被改坏，好数据就被覆盖了。

对应的补法：每月把 `/opt/1panel/backup` 里最新的包下载一份到本机；异地对象存储（OSS）列为下一阶段——需要先开通账号，再在面板里配备份账号。真正可靠的状态是 **3-2-1**：三份副本、两种介质、一份异地。现在只做到了"三份副本"。

## 顺带做的两件事

**日志轮转**。OpenResty 的 access log 不轮转就会一直涨，把磁盘吃满——而磁盘满会连带让备份失败。加了 `/etc/logrotate.d/openresty-site`：每周轮转、保留 4 份、压缩、`copytruncate`（不重启服务）。配置文件也放进了仓库，换机器直接复制。

**恢复前先手动备份一次**。这是 1Panel 文档里的建议，但在慌乱时最容易忘：恢复会覆盖当前状态，如果当前状态其实还有救，先留一份再说。

## 复盘

备份这件事，价值不在"每天跑了个任务"，而在三个问题的答案：

1. 备份包**能解开**吗？（演练）
2. 恢复流程**走过**吗？（演练 + 文档）
3. 最坏情况下**还有一份在别处**吗？（异地化，待做）

第 1、2 条已经做到了，第 3 条是下一步。写下来提醒自己：**没有演练过的备份，只能叫"希望"**。
